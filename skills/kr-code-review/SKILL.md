# 한국어 코드 리뷰 스킬

## 이 스킬이 하는 일

PR의 변경분을 읽고 **실제로 깨질 수 있는 것**을 찾아 한국어 인라인 코멘트로 남긴다.

## 이 스킬이 하지 않는 일 (경계)

- ❌ **코드를 수정하지 않는다.** 리뷰는 읽기 전용이다. 수정은 작성자의 몫이다.
- ❌ **머지하지 않는다. 승인(Approve)하지 않는다.** 사람의 권한이다.
- ❌ **스타일 취향을 말하지 않는다.** 포매터와 린터가 할 일이다.
- ❌ **"이 부분 확인 부탁드립니다" 같은 빈 코멘트를 남기지 않는다.**
  무엇이 어떻게 잘못되는지 말하지 못하면 남기지 않는다.

## 전제 조건

- Paperclip 작업으로 배정되어 실행된다. 작업 맥락은 `paperclip` 스킬로 읽는다.
- GitHub 쓰기 권한이 필요하다. 없으면 리뷰 결과를 작업 스레드에 남기고
  사람이 옮겨 붙일 수 있게 한다. **권한을 우회하려 하지 않는다.**

## 작업 순서

### 1. 맥락을 먼저 읽는다

```
① 작업(Task) 설명 — 이 PR이 무엇을 하려는 것인가
② 연결된 목표(Goal) — 왜 하는가
③ PR 본문과 제목
④ 저장소 규약 — AGENTS.md, CONTRIBUTING.md, CLAUDE.md, DESIGN.md
```

**④를 건너뛰지 말 것.** 저장소 규약을 모르고 하는 지적은 대부분 틀린다.
이 저장소의 경우 `DESIGN.md`(디자인 토큰 규칙)와 `AGENTS.md`가 특히 중요하다.

### 2. diff를 읽는다

변경된 줄만 보지 말고 **그 줄이 호출되는 경로**를 확인한다.
호출자를 모르면 그 지적은 추측이다.

### 3. 지적을 분류한다

| 등급 | 기준 | 표기 |
|---|---|---|
| **blocker** | 머지되면 깨진다. 데이터 손상·보안·크래시·회귀 | 🔴 |
| **should** | 깨지진 않지만 고쳐야 한다. 누락된 에러 처리, 경계값, 테스트 공백 | 🟡 |
| **nit** | 고쳐도 되고 안 고쳐도 된다 | ⚪ |

**⚪ nit은 PR당 3개를 넘기지 않는다.** 그 이상은 노이즈고, 노이즈가 많으면
🔴을 읽지 않게 된다. 리뷰의 가치는 지적 개수가 아니라 신호 대 잡음비다.

### 4. 각 지적을 검증한다 — 이 단계를 생략하지 말 것

코멘트를 남기기 전에 **실패 경로를 구체적으로 적을 수 있는지** 자문한다.

> "어떤 입력/상태가 들어오면, 어디서, 어떻게 잘못되는가?"

이 문장을 못 쓰면 그 지적은 **추측이다. 남기지 않는다.**

가능하면 실제로 돌려서 확인한다:
```bash
pnpm typecheck
pnpm test <관련 테스트 파일>
```

### 5. 코멘트를 쓴다

**형식**

```
🔴 <한 줄 요약>

<무엇이 문제인지 1~2문장>

**재현**: <어떤 입력/상태에서 어떻게 깨지는지>

**제안**:
```<언어>
<수정 코드>
```
```

**문체 규칙**
- 사람이 아니라 **코드**를 지적한다. "이렇게 짜시면 안 됩니다" ❌ → "이 경로에서 X가 null이면 터집니다" ✅
- 단정할 수 없으면 단정하지 않는다. "확인이 필요합니다"가 아니라
  **"A 조건에서는 B가 되는데, 의도한 동작인가요?"** 로 묻는다.
- 존댓말 평서체. `~합니다`, `~됩니다`. 명령조(`~하세요`)는 제안 코드에만 쓴다.
- 용어는 `mvp/glossary-ko.md` 를 따른다.

### 6. 요약 코멘트를 남긴다

```markdown
## 리뷰 요약

| 등급 | 수 |
|---|---|
| 🔴 blocker | N |
| 🟡 should | N |
| ⚪ nit | N |

<전체 평 2~3문장. 머지 가능 여부와 그 이유.>

<리뷰하지 못한 부분이 있으면 명시한다. 예: "마이그레이션 SQL은
실제 데이터로 검증하지 못했습니다.">
```

**마지막 문단을 빠뜨리지 말 것.** 리뷰하지 않은 것을 리뷰한 척하면
리뷰 전체의 신뢰가 깨진다.

### 7. 작업을 완료 처리한다

Paperclip 작업에 결과를 보고한다. 🔴이 하나라도 있으면
**작업을 `done`이 아니라 `in_review`로 둔다.** 사람이 판단할 몫이다.

## 성공 판정 기준

이 스킬은 아래 지표로 평가된다 (`mvp/01-MVP-DESIGN.md` M3).

| 지표 | 목표 | 측정 방법 |
|---|---|---|
| **지적 유효율** | ≥ 50% | 사람 리뷰어가 "유효"로 판정한 지적 / 전체 지적 |
| 🔴 오탐율 | ≤ 10% | 틀린 blocker / 전체 blocker |
| 누락률 | 사람이 추가로 찾은 🔴 수 | 적을수록 좋다 |

> **지적을 많이 남기는 쪽으로 최적화하지 말 것.** 유효율이 지표다.
> 확신 없는 지적 5개보다 확실한 지적 1개가 낫다.
