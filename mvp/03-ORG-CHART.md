# M4 — 에이전트 조직도 설계

> 런타임 결정: **Claude Code** (`packages/adapters/claude-local`)
> 이 문서는 "누구를 몇 명 채용할 것인가"를 정한다.

## 원칙 — 작게 시작한다

업스트림 README는 "CEO, CTO, 엔지니어, 디자이너, 마케터"를 예로 든다.
**MVP에서 그렇게 하면 안 된다.** 이유:

1. 에이전트 수에 비례해 **비용이 선형으로 는다.** 검증 전에 쓸 돈이 아니다.
2. 에이전트가 많으면 **어느 에이전트가 가치를 냈는지 분리가 안 된다.**
   M5의 "에이전트 1명당 월 원가" 지표를 못 뽑는다.
3. 위임 체인이 길어지면 **실패 원인 추적이 불가능해진다.**

→ **4명으로 시작한다.** 효용이 증명된 역할만 늘린다.

## 조직도 (MVP)

```
                    사람 (운영자)
                        │  승인 게이트
                        ▼
                   CTO 에이전트
                   (조율·위임만)
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   리뷰어          엔지니어          리서처
 (kr-code-review)  (구현)          (조사·문서)
```

| # | 역할 | 하네스 | 주 업무 | 권한 |
|---|---|---|---|---|
| 1 | **CTO** | Claude Code | 작업 분해·위임·주간보고 | 채용 ❌ / 머지 ❌ |
| 2 | **리뷰어** | Claude Code | PR 리뷰 (`kr-code-review`) | 쓰기 ❌ (코멘트만) |
| 3 | **엔지니어** | Claude Code | 구현·테스트 | PR 생성 ⭕ / 머지 ❌ |
| 4 | **리서처** | Claude Code | 기술 조사·문서화 | 코드 쓰기 ❌ |

**4명 전원 머지 권한 없음.** 머지는 사람이 한다. 예외 없음.

## 왜 리뷰어를 엔지니어와 분리하는가

같은 에이전트가 짜고 리뷰하면 **자기 코드를 통과시킨다.** 역할 분리는
조직 설계가 아니라 **신뢰성 장치**다. Paperclip의 조직도는 이걸 강제할 수 있다.

## 권한·승인 게이트 설정

```
승인 필요 (사람):
  - PR 머지
  - 비밀정보 접근 권한 부여
  - 에이전트 추가 채용
  - 예산 상향

자동 허용:
  - PR 생성, 코멘트
  - 작업 생성·배정 (CTO만)
  - 조사·문서 작성
```

> ⚠️ **첫 주에 승인 게이트를 끄지 말 것.** 에이전트가 승인 없이 저장소에
> 쓰기 시작하면 첫 사고 한 번으로 팀 전체가 이 도구를 불신하게 된다.
> 신뢰는 게이트를 천천히 푸는 방식으로만 쌓인다. 반대 순서는 복구가 안 된다.

## 예산

| 범위 | 한도 | 초과 시 |
|---|---|---|
| 회사 전체 | 월 상한 설정 | **자동 정지** |
| 에이전트별 | 각자 상한 | 해당 에이전트만 정지 |
| 프로젝트별 | 실험 단위 상한 | 해당 프로젝트 정지 |

3단계를 **전부 켠다.** 회사 상한만 켜면 에이전트 하나가 폭주했을 때
전사가 멈춘다. 에이전트별 상한이 폭발 반경을 가둔다.

금액은 1주 실사용 데이터로 정한다. **지금 추측으로 정하지 않는다** —
M5의 목적이 바로 이 숫자를 얻는 것이다.

## 루틴 (Scheduled Routines)

| 루틴 | 주기 | 담당 | 산출물 |
|---|---|---|---|
| 주간보고 | 금 17:00 | CTO | 작업·비용·블로커 집계 (한국어) |
| 업스트림 동기화 점검 | 월 10:00 | 엔지니어 | `git fetch upstream` 차이 보고 |
| 예산 점검 | 매일 09:00 | CTO | 소진율·이상치 알림 |

## 확장 판정 기준

아래를 **전부** 충족하면 역할을 추가한다. 하나라도 미달이면 늘리지 않는다.

- 기존 4명의 작업 큐가 실제로 밀리고 있다 (대기 작업이 쌓인다)
- 추가하려는 역할의 업무가 **기존 역할과 명확히 분리**된다
- 그 역할의 산출물에 **성공 판정 기준을 쓸 수 있다**
- 예산 여유가 있다

> "있으면 좋을 것 같아서" 채용하지 않는다. 그게 비용이 새는 방식이다.
