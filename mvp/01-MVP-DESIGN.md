# MVP 설계서

> 전제: Paperclip 포크 위에 커스터마이징 / 수익화 목표 = 국내 + 해외
> 선행 분석: [00-UPSTREAM-ANALYSIS.md](./00-UPSTREAM-ANALYSIS.md)

## 0. 솔직한 전제 하나

업스트림 ROADMAP은 거의 다 ✅다. **기능을 더 만들어서 이기는 게임이 아니다.**
그리고 업스트림은 자체 Cloud로 호스팅을 팔 예정이다. 호스팅 재판매로 글로벌에서
정면 승부하면 진다.

우리가 이길 수 있는 축은 셋뿐이다.

1. **현지화** — 한국어가 0%다. 국내 기업은 지금 이 제품을 못 쓴다.
2. **고객 과금** — 결제 레이어가 없다. 재판매하려면 누군가는 만들어야 한다.
3. **도메인 특화** — 특정 업무 흐름을 스킬/플러그인으로 포장한 것.

MVP는 이 셋 중 1번에 집중하고, 2번의 뼈대를 깔고, 3번은 우리가 직접 써보며 찾는다.

## 1. MVP 정의 (한 문장)

> **"우리 개발팀이 한국어로 실제 업무를 돌리는 Paperclip 인스턴스."**

내부 도구가 아니라 **판매 가능한 제품의 0번 고객이 우리 자신**인 구조다.
팔 수 있는지 알아보는 가장 싸고 빠른 방법은 우리가 먼저 쓰는 것이다.

### MVP 범위 (In)

| # | 산출물 | 왜 |
|---|---|---|
| M1 | **Paperclip 사내 인스턴스 구동** (Docker, 우리 PostgreSQL) | 모든 것의 전제 |
| M2 | **한국어 UI — 핵심 20개 화면** | 국내 판매의 최소 조건 |
| M3 | **우리 업무 스킬 3종** (코드리뷰 / 이슈 트리아지 / 주간보고) | 실효용 증명 |
| M4 | **에이전트 조직도 1개** (CTO 1 + 엔지니어 2 + 리서처 1) | 도그푸딩 단위 |
| M5 | **비용 대시보드 운영** (예산·알림·자동정지 실사용) | 수익모델 근거 데이터 |

### MVP 범위 밖 (Out — 의도적으로 제외)

- ❌ 결제/구독 과금 → Phase 2. **매출 가설이 검증되기 전에 만들면 낭비다.**
- ❌ 1,208개 .tsx 전수 한국어화 → 핵심 20화면만. 나머지는 영문 유지.
- ❌ 마케팅/콘텐츠 에이전트 → Phase 1-B. 개발팀 사례부터 끝낸다.
- ❌ 외부 고객 온보딩 → Phase 2.
- ❌ 코어(`server/src/services/*`) 수정 → 업스트림 추종 불가해진다.

## 2. 아키텍처 원칙 — "코어를 고치지 않는다"

업스트림은 5,302 커밋에 브랜치 1,198개다. 코어를 건드리면 6개월 뒤
머지 불가능한 고아 포크가 된다. 그래서 변경을 **가장자리에 가둔다.**

```
우리 코드가 사는 곳 (업스트림과 충돌 없음)
├── mvp/                           ← 문서·운영 스크립트 (신규 디렉터리)
├── packages/plugins/kr-*/         ← 국내 전용 플러그인
├── packages/adapters/kr-*/        ← 국내 전용 어댑터
├── skills/kr-*/                   ← 우리 업무 절차
└── ui/src/i18n/locales/ko.json    ← 번역 (데이터 파일, 충돌 거의 없음)

조심해서 건드리는 곳 (머지 충돌 발생 지점)
└── ui/src/**/*.tsx                ← 문자열 외부화. codemod로만. 손수정 금지.
```

**업스트림 추종**: 주 1회 `git fetch upstream && git merge upstream/master`.
충돌이 나면 그 주에 바로 해결한다. 밀리면 복구 비용이 지수로 커진다.

## 3. M2 — 한국어화를 실제로 해내는 방법

이게 MVP에서 가장 어렵고 가장 가치 있는 부분이다. 정면 돌파는 불가능하다.

**문제**: `.tsx` 1,208개, 문자열 전부 하드코딩. `useTranslation` 실사용 파일 = 1개.

**해법 — 3단 파이프라인** (`DESIGN.md` 원칙 "codemod via committed scripts" 준수):

```
① 추출   scripts/kr/extract-strings.mjs
         대상 20개 화면의 JSX 텍스트 노드/aria-label/placeholder를
         AST로 스캔 → 안정적 키 생성 (파일경로 기반 해시)
         → ui/src/i18n/locales/en.json 에 적재

② 치환   scripts/kr/codemod-i18n.mjs
         원문 → t("key") 로 기계 치환. 손수정 금지.
         Storybook 비주얼 스냅샷으로 "시각적 무변화" 증명 (DESIGN.md 요구사항)

③ 번역   scripts/kr/translate-locale.mjs
         en.json → ko.json. LLM 1차 번역 + 용어집 강제 + 사람 검수.
         용어집: mvp/glossary-ko.md 에 고정 (task=작업, agent=에이전트,
         heartbeat=하트비트, goal=목표, company=회사 — 한 개념 한 단어)
```

**대상 20개 화면 (우선순위 순)**
온보딩 · 대시보드 · 작업목록 · 작업상세/스레드 · 에이전트목록 · 에이전트상세 ·
조직도 · 목표 · 프로젝트 · 예산/비용 · 승인대기 · 활동로그 · 스킬목록 ·
스킬스튜디오 · 연결된앱 · 비밀관리 · 설정 · 회사전환 · 검색 · 알림

**검증**: `pnpm build` · `pnpm typecheck` · `pnpm build-storybook` 통과 +
Storybook 스냅샷이 baseline과 일치 (= 한국어 전환이 레이아웃을 깨지 않음).

> ⚠️ 한국어는 영어보다 길어지는 구간이 있다. 버튼·배지·테이블 헤더에서
> 깨짐이 나온다. 스냅샷 비교가 이걸 잡는 유일한 방법이다.

## 4. M3 — 우리 업무 스킬 3종

도그푸딩의 실체. 각 스킬은 `skills/kr-*/SKILL.md` 로 커밋한다.

| 스킬 | 입력 | 에이전트 행동 | 산출물 | 성공 판정 |
|---|---|---|---|---|
| `kr-code-review` | PR 열림 | diff 분석 → 인라인 코멘트 | PR 리뷰 | 사람 리뷰어가 "유효" 판정한 지적 비율 ≥ 50% |
| `kr-issue-triage` | 신규 이슈 | 라벨·담당·우선순위 제안 | 이슈 업데이트 | 제안 수용률 ≥ 70% |
| `kr-weekly-report` | 매주 금 17시 루틴 | 작업·비용·블로커 집계 | 한국어 주간보고 | 사람이 수정 없이 쓸 수 있는가 |

**루틴(Scheduled Routines)**과 **승인 게이트(Approvals)**를 반드시 켠다.
에이전트가 승인 없이 PR에 쓰게 두면 첫 주에 신뢰를 잃는다.

## 5. M5 — 수익모델 근거 데이터 수집

MVP를 돌리는 **진짜 목적**은 아래 숫자를 얻는 것이다. 이 숫자 없이는
가격을 정할 수 없고, 가격 없이는 팔 수 없다.

| 측정 항목 | 어디서 | 왜 필요한가 |
|---|---|---|
| 에이전트 1명 월 토큰 비용 | `cost_events` 원장 | 원가 → 마진 설계 |
| 작업 1건당 평균 비용 | 비용/작업 집계 | 사용량 과금 단가 |
| 사람 개입률 (승인·반려·재작업) | 활동로그 | 자율성 수준 = 가치 주장 근거 |
| 절감 공수 (시간) | 주간보고 수기 기록 | **고객 제안서의 ROI 숫자** |
| 실패/복구율 | 실행 복구 로그 | SLA 설계 |

목표: **4주 운영 후 "에이전트 1명당 월 원가 ₩X, 절감 공수 Y시간"을 말할 수 있다.**

## 6. 일정 (6주)

| 주 | 내용 | 완료 기준 |
|---|---|---|
| W1 | M1 인스턴스 + M4 조직도 + 어댑터 연결 | 에이전트가 작업 1건 완수 |
| W2 | M3 스킬 3종 작성·평가 | Skill Studio 평가 통과 |
| W3 | M2 ① 추출 + ② 치환 codemod | 스냅샷 무변화 증명 |
| W4 | M2 ③ 번역 + 검수 | 20개 화면 한국어 동작 |
| W5 | M5 데이터 수집 + 업스트림 머지 | 원가 지표 산출 |
| W6 | 회고 → Phase 2 Go/No-Go | **아래 판정 기준으로 결정** |

## 7. Go / No-Go 판정 기준 (W6)

수익화로 넘어갈지 여기서 정직하게 판단한다.

**Go 조건 (전부 충족해야 함)**
- 스킬 3종 중 **2종 이상**이 사람 개입 없이 주 5회 이상 가치 있는 산출물 생성
- 에이전트 1명 월 원가가 **사람 공수 절감 가치보다 명백히 낮음**
- 외부에 보여줄 수 있는 한국어 데모가 존재
- 유료로 쓸 의향을 밝힌 잠재 고객 **3곳 이상** 확보 (아직 계약 아님, 인터뷰면 충분)

**No-Go면** → Phase 2를 건너뛰고 사내 도구로만 유지. 손실은 6주로 끝난다.

## 8. Phase 2 — 수익화 (Go일 때만)

> **첫 매출은 SaaS 구독이 아니라 구축 대행(SI)에서 나올 가능성이 높다.**
> 국내 AI 에이전트 오케스트레이션 시장은 아직 "이게 뭔지 설명해야 하는" 단계다.
> 설명 비용을 컨설팅 매출로 회수하면서 SaaS 전환을 준비하는 게 현실적이다.

| 단계 | 모델 | 구축 필요 |
|---|---|---|
| 2-A | **구축 대행 + 운영 지원** | 없음. 지금 포크로 즉시 가능 |
| 2-B | **관리형 호스팅** (국내 B2B) | 멀티테넌트 운영 + 구독 결제 |
| 2-C | **셀프서브 SaaS** (국내+해외) | 셀프 온보딩 + 사용량 과금 |

**결제 레이어 (2-B부터 필요 — 신규 모듈, 코어 무수정)**
- 국내: 토스페이먼츠 or PortOne (정기결제·현금영수증·세금계산서)
- 해외: Stripe Billing
- 신규 테이블: `subscriptions`, `plans`, `usage_records`, `customer_invoices`
  → 기존 `cost_events`(원가)와 **분리**한다. 원가 원장과 매출 원장을 섞으면
    나중에 마진 계산이 불가능해진다.

**국내 필수 연동 (2-B)**: 카카오워크/네이버웍스 알림, 세금계산서,
개인정보 국내 리전 보관.
